## 🔍 深度分析

### 1. 硬件加速的影响

#### AES性能变化：
- **启用AES-NI**: Sign 95.8ms, Verify 85.6ms
- **禁用AES-NI**: Sign 139.7ms (+45.8%), Verify 162.7ms (+90.0%)
- **AES-NI加速比**: Sign约 **1.46x**, Verify约 **1.90x**

**结论**: AES-NI硬件加速为AES提供了 **46-90%** 的性能提升，Verify操作受益更明显。

#### SM4性能变化：
- **有AES-NI环境**: Sign 331.9ms, Verify 349.2ms
- **无AES-NI环境**: Sign 350.1ms (+5.5%), Verify 369.5ms (+5.8%)  
- **性能差异**: 几乎没有变化（<6%）

**结论**: SM4始终使用纯软件实现，不受AES-NI影响。轻微变化可能来自CPU频率波动或系统负载。

---

### 2. SM4比AES慢的原因

#### 在硬件加速环境下（AES-NI启用）：
- **SM4比AES慢 3.46-4.08倍** (Sign/Verify)
- **主要原因**: AES享受硬件加速（80%+性能来自AES-NI），SM4无硬件支持

#### 在纯软件环境下（所有优化禁用）：
- **SM4比AES慢 2.27-2.51倍** (Sign/Verify)
- **主要原因**: 算法本身的架构差异

---

### 3. 算法架构层面差异

#### 轮数差异：
|   | AES-128 | SM4 |
|---|---------|-----|
| **轮数** | 10 | 32 |
| **密钥扩展** | 10轮密钥 | 32轮密钥 |

**影响**: SM4的32轮迭代是AES的3.2倍，直接增加计算量

#### 轮函数复杂度：

**AES轮函数**（10轮）:
1. SubBytes (S-box替换)
2. ShiftRows (行移位)  
3. MixColumns (列混合) - 最后一轮除外
4. AddRoundKey (密钥加)

**SM4轮函数**（32轮）:
1. 非线性变换 τ (S-box，8→8映射)
2. 线性变换 L (循环移位+异或)
3. 合成置换 T = L ∘ τ
4. 密钥加
5. 三个字的移位

**软件实现差异**:
- **AES S-box**: 8位输入→8位输出，查表高效（256字节表）
- **SM4 S-box**: 同样8→8映射，但需要4次查表（4个S盒合并优化后性能类似）
- **AES MixColumns**: 可用查表法加速（T-table优化）
- **SM4线性变换L**: 需要循环移位+多次异或，软件实现开销较大

#### 数据依赖性：
- **AES**: 列混合操作有更好的并行性
- **SM4**: Feistel结构导致更强的数据依赖，降低指令级并行度

---

### 4. 硬件实现差异

#### AES硬件加速（AES-NI）:
```c
// 一条指令完成整个AES轮
__m128i m = _mm_aesenc_si128(state, round_key);
```
- **每轮 = 1条CPU指令**（含SubBytes+ShiftRows+MixColumns+AddRoundKey）
- **延迟隐藏**: 流水线可并行处理多个块
- **密钥扩展**: `_mm_aeskeygenassist_si128()` 硬件指令

**性能**: 10轮AES ≈ 10条指令 + 流水线优化

#### SM4软件实现:
```c
// 32轮迭代，每轮都是软件操作
for (int i = 0; i < 32; i++) {
    X[i+4] = X[i] ^ sm4_t(X[i+1] ^ X[i+2] ^ X[i+3] ^ rk[i]);
}
```
- **每轮 ≈ 数十条CPU指令**（S-box查表+移位+异或+内存访问）
- **无硬件加速支持**（除少数国产CPU支持GM/T指令集）
- **32轮** = 大量分支和存储访问

**性能**: 32轮SM4 ≈ 数百至上千条指令

---

### 5. 为什么纯软件下SM4仅慢2.5倍？

这是个有趣的观察！当去除AES硬件加速后，性能差距从 **4x 缩小到 2.5x**。

#### 原因分析：

**1. AES失去硬件加速的代价很大**:
- AES-NI: 10轮 ≈ 10条指令
- 软件AES: 10轮 ≈ 200-400条指令（查表+移位+异或+MixColumns）
- **性能下降**: 约 1.5-2x

**2. SM4软件实现相对更优化**:
- 虽然有32轮，但每轮的软件实现已经高度优化（查表法）
- Feistel结构在软件上实现相对简洁

**3. FAEST协议开销占比**:
- 签名过程包含: 密钥生成 + Vizing树 + VOLE + 挑战响应
- 纯密码算法（AES/SM4）只是其中一部分
- 当AES从硬件退化到软件后，非密码部分的开销占比增加，掩盖了部分性能差异

**4. 轮数vs单轮复杂度的权衡**:
- AES: 10轮，但软件MixColumns非常复杂
- SM4: 32轮，但Feistel结构每轮相对简单
- 在软件实现下，两者的 **总指令数** 差距小于轮数差距（32/10 = 3.2x）

## 💡 优化建议

### 场景1: 性能优先（国际应用）
**推荐**: FAEST_128S (AES) + AES-NI启用
```
Sign:   95.8 ms   ✓ 最快
Verify: 85.6 ms  
签名:   4.5 KB    ✓ 较小
```

### 场景2: 国密合规要求
**推荐**: FAEST_SM4_128S (SM4纯软件)
```
Sign:   350.1 ms  ✗ 较慢（3.46x）
Verify: 369.5 ms  
签名:   7.1 KB    ✗ 较大（1.58x）
```
**优化路径**:
1. 等待SM4硬件加速支持（国产CPU GM/T指令集）
2. SIMD优化（AVX2并行处理多个块）
3. 考虑使用EM模式减少约50%时间和25%签名大小

### 场景3: 性能与体积平衡
**推荐**: FAEST_EM_128S / FAEST_EM_SM4_128S
```
FAEST_EM_128S:       Sign 42.7ms,  签名 3.9KB
FAEST_EM_SM4_128S:   Sign 150.9ms, 签名 4.8KB
```
- EM模式比标准模式快 **2-2.3倍**
- 签名大小减少 **15-32%**
